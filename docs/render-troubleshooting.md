# Video build and render troubleshooting

Use this guide to recover an existing video job. Run commands from the repository root and replace
`jobs/<slug>` with the actual job directory. Examples quote that placeholder so the shell does not interpret
its angle brackets. Keep using the repository wrapper; do not invoke HyperFrames directly, upgrade it during
recovery, or edit `node_modules`.

## Build failures are classified before repair

A failed build is not automatically a film defect. Missing tools or modules, a browser that cannot launch, a full
disk, a permission error or a network failure produce `STATE: infrastructure blocked`. That state names the actual
environment errors and asks you to fix them, then rerun `build`; it does **not** write a director or builder repair
brief. Missing assets, invalid `film.json`, unspoken cue words and broken motion remain film repairs and go to the
scene owner. If both kinds appear together, fix the environment first; the film errors are still listed so nothing is
hidden.

## How a render runs by default

- **Two capture workers.** `render` asks HyperFrames for 2 workers and turns off its low-memory mode, which
  otherwise pins machines with 8 GB of RAM or less to one. If that render fails, it is retried once with the
  renderer's own low-memory defaults. Set another count with `--workers <n|auto>` or `VIDEO_RENDER_WORKERS`;
  `--workers 1` keeps low-memory mode.
- **Every render covers the whole film.** There is no prototype cut. A review pack may sample a shorter interval,
  but it reads the completed film and the delivered MP4 always has the film's full length.

## Start with the saved state

```bash
npm run video -- next --job "jobs/<slug>"
```

Follow the reported step. Preserve the existing audio, script, scene files, assets, and job configuration.
Read saved briefs and prior session notes when resuming another agent's work. Do not create a replacement job
just because the previous session stopped.

| Symptom | First action |
|---|---|
| `JavaScript heap out of memory` | Check available memory, then retry with a larger Node heap. |
| Quiet build or render | Check process activity and output growth before calling it hung. |
| Competing headless browsers after a crash | Identify and stop only orphaned browsers belonging to the failed job. |
| Browser startup says `Operation not permitted` | Check the execution sandbox and retry through the harness's permitted execution path. |
| Unknown `compile` or `assemble` command | Use `build` for a `film.json` job; the older workflow has been retired. |
| `Unknown command` or `Expected --option value` | Consult the wrapper's help and correct the command or option syntax. |
| `next` still requests a full build | Check whether the last build was scene-scoped, stale, failed, or incomplete. |
| Slow screenshot capture or automatic one-worker selection | Inspect capture logs and resource use before changing capture settings or worker count. |
| Overlapping actions or ambiguous cue occurrences | Follow the repair briefs generated by `next`. |
| Loudness below target despite compliant peaks | Inspect the mix measurements and identify what limits the master gain. |

## Node runs out of heap memory

Typical errors include:

```text
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
FATAL ERROR: Ineffective mark-compacts near heap limit
```

1. Confirm that the process actually exited with an out-of-memory error. Silence alone is insufficient.
2. Check available system memory and competing processes. A larger JavaScript heap does not provide more
   physical RAM; Chrome, FFmpeg, Python, and the operating system also need memory.
3. Where the machine has capacity, retry the reported command with a 4 GB Node heap:

   ```bash
   env NODE_OPTIONS=--max-old-space-size=4096 \
     npm run video -- build --job "jobs/<slug>"
   ```

   Apply the same environment setting when subsequently rendering:

   ```bash
   env NODE_OPTIONS=--max-old-space-size=4096 \
     npm run video -- render --quality delivery --job "jobs/<slug>"
   ```

4. Keep the setting on each invocation that needs it. Setting it for one command does not persist it for
   later commands. Preserve any other required `NODE_OPTIONS` when constructing the environment.
5. Confirm that the command finishes successfully. For a build, require the complete build result rather
   than assuming that exceeding the old memory limit proves success.

If memory still runs out, reduce concurrent work and diagnose memory use before increasing the limit again.
A heap error and an operating-system memory kill are different failures.

## Failed attempts leave orphaned browsers

A crashed or interrupted parent process can leave headless Chrome consuming CPU and memory. Starting more
builds can then make recovery slower or cause another memory failure.

On Linux, inspect the process tree and resource use:

```bash
ps -eo pid,ppid,etime,%cpu,%mem,stat,comm,args --sort=-%cpu
```

Identify the failed job's browser parents using their ancestry, launch time, automation arguments, and temporary
profile. A reparented process is a clue, not sufficient proof of ownership. Stop only confirmed orphaned
processes, using a graceful termination first:

```bash
kill -TERM PID
```

Replace `PID` with the confirmed process ID. Verify that its children exit before restarting the job. Do not use
a blanket Chrome kill or terminate another job's active renderer or the person's browser.

A sandbox may expose only its own process namespace. An empty sandbox process listing does not prove that
host processes have exited. Use the harness's permitted host diagnostics when needed. After cancelling a
render, check cleanup rather than assuming every child received the cancellation signal.

## The sandbox blocks Chromium startup

Errors such as the following can indicate an execution restriction:

```text
Failed to launch the browser process
setsockopt: Operation not permitted (1)
```

Read the actual browser error. If it points to a sandbox restriction, retry the same wrapper command using the
harness's permitted execution path outside that restriction. Retain the memory settings needed by the job and
honor existing user authorization and approval policy. Do not repeatedly request authorization already granted.

Confirm that the browser launches and the build or render advances. An execution permission failure does not
justify editing scenes, upgrading dependencies, disabling unrelated protections, or replacing narration.

## A command is unknown

Production jobs use `film.json` and `build` to compile and inspect scenes. The earlier `beats.json` workflow
and its `compile` / `assemble` commands have been retired. Recreate an older job from its saved script and
recording using `start`, then follow `next`. Do not fabricate an empty beat grid or replace the recording.

For an unsupported command, consult the repository wrapper:

```bash
npm run video -- help
```

Do not assume that a command described by a HyperFrames skill is exposed by `npm run video`. Commands such as
`doctor` and standalone `beats` are not wrapper commands. If an error remains unactionable after consulting help,
report its exact text and the last valid checkpoint.

The wrapper requires option values. Use `--reuse-build true`, not a bare `--reuse-build`. Run `setup-audio` for
missing audio tools; it does not repair unrelated heap, browser, or workflow errors.

## A scene build does not qualify as a full build

`build --scene <id>` can compile the entire film while inspecting only the selected scene. Its build receipt is
scene-scoped. It does not establish that every scene passed browser checks, and `next` may still request a full
build.

Follow the reported full-build step:

```bash
npm run video -- build --job "jobs/<slug>"
```

Confirm that `review/build.json` records a successful current build with `scope: all`, no errors, and no missing
scenes. Check the compiled missing-scene list as well as the presence of scene files. A valid plan or a directory
full of scene JSON files alone does not establish completeness.

### Reuse an unchanged successful build

When retrying capture after a successful full build, avoid repeating expensive browser inspection:

```bash
npm run video -- render --quality delivery --reuse-build true --job "jobs/<slug>"
```

The wrapper accepts reuse only when the full build is successful, its source fingerprint matches, no scenes are
missing, and every compiled scene has an inspection record. Stale, partial, failed, or uninspected builds are
rejected. If rejected, follow `next` and rebuild; never edit a receipt or hash to force acceptance.

Build reuse skips repeated build work. Rendering still performs its audit, lint, mixing, verification, and encoded
picture checks. It does not waive review or delivery requirements.

## Capture is slow or automatically uses one worker

First identify the active capture path and resource limits from the render logs:

- `screenshot` with software graphics can be slow on complex compositions.
- The renderer's automatic low-memory profile can force screenshot capture and one worker.
- `beginframe` is an alternative capture path when supported by the installed browser and composition.
- Auto calibration can reduce worker count for expensive captures even when a higher maximum was configured.

Keep a progressing render running while diagnosing it. Compare the cost of restarting with its remaining work;
do not repeatedly abandon substantial completed capture to try speculative settings.

When the logs establish low-memory mode as the bottleneck and the machine has sufficient memory, try the
installed renderer's supported environment overrides through the wrapper:

```bash
env NODE_OPTIONS=--max-old-space-size=4096 \
  PRODUCER_LOW_MEMORY_MODE=false \
  PRODUCER_FORCE_SCREENSHOT=false \
  npm run video -- render --quality delivery --reuse-build true \
    --workers 2 --job "jobs/<slug>"
```

Use `--reuse-build true` only with a qualifying full build. Choose the heap and worker count for the machine;
this example is not a universal resource prescription. Check that the installed version supports these settings.

`PRODUCER_MAX_WORKERS` sets a maximum; it does not force that many workers. The wrapper's explicit `--workers`
option forwards the requested count to the renderer and can override automatic worker reduction. Each worker
adds a browser and resource demand. Start conservatively and confirm actual worker launches, memory use, and
capture progress. More workers can be slower or exhaust memory.

Disabling low-memory mode does not guarantee BeginFrame capture or a speedup. Confirm the selected path in the
logs. If an optional static-frame deduplication scan repeatedly consumes its time budget, `HF_STATIC_DEDUP=false`
can disable that scan; it does not remove frames or animation. Change only settings relevant to the observed
bottleneck, and preserve resolution, frame rate, duration, and requested quality.

## A quiet process looks stalled

The wrapper runs the renderer quietly, so capture may produce no console output for minutes. Check several
indicators over time:

1. Whether the actual build, browser, encoder, or audio process is still running.
2. CPU and memory activity, allowing for blocking on another stage.
3. Growth or updates in the current render's working files.
4. A terminal success or failure result and the pipeline's saved state.

File growth establishes activity, not completion. In-progress MP4 files can lack their final index and fail
`ffprobe`; that alone does not establish corruption. Report exact percentages only from a reliable progress
source. Counting H.264 units in a partial MP4 is encoder-specific and is not a general frame-counting method.

If a read-only debugging probe fails, distinguish that diagnostic failure from a render failure. Temporary browser
profile arguments and debugging endpoints are not stable progress APIs. Fall back to process and output activity.

## Timing errors block the build

For overlapping actions, unknown cues, or repeated cue phrases, run `next` and delegate the generated repair
briefs to the named owners. The orchestrator does not directly edit shots or evidence.

Builders should check:

- Whether the earlier action, including staggered elements, ends before a conflicting action begins.
- Whether a cue resolved to the intended spoken occurrence. A repeated phrase may require an explicit
  `occurrence`; moving an action is not a substitute for correcting the wrong narration anchor.
- Whether shortening a duration or adjusting a cue-relative offset preserves the intended explanation.

After scoped repairs pass, follow `next` through the full build. Do not hide errors by editing reports. Style
warnings remain findings to evaluate through the normal review process, even when they do not block compilation.

## Sources become stale during rendering

The job fingerprint includes production inputs, assets, composition files, configuration, and other non-excluded
job files. Adding a recovery note inside the job can invalidate a build or an in-progress render even when the
pictures did not change.

Keep troubleshooting notes under repository `docs/`, outside the job. Let pipeline commands manage their own
outputs. Do not hand-edit generated receipts, reviewer reports, or evidence. If production sources change, rebuild
and render the changed version; do not alter hashes to make old output appear current. Avoid opening Studio or
`preview` during recovery because they can rewrite job files.

## The MP4 is quieter than the loudness target

Inspect `review/mix.json` and `review/render-verification.json`. Read integrated LUFS, stereo and mono true/sample
peaks, `limitedBy`, and narration-masking findings. Measurements must come from the exported MP4.

The pipeline aims for approximately −16 LUFS while keeping peaks at or below −4 dB. If `limitedBy` is the peak
ceiling, raising the master gain further would violate that ceiling. Peak compliance does not establish that the
integrated loudness target was reached.

Route masking or dominant-effect findings through the repair briefs. Builders can lower effects or music and
rebuild; use the pipeline's `mix` command only when it accepts the current picture and source receipt. Source
changes may require a new render. Do not force compliance by clipping the output, processing supplied narration
beyond its permitted master gain, or replacing the recording with TTS. If the constraints still prevent the target,
record the measured shortfall as a limitation. See [Sound and mixing](sound.md).

Waveform correlation is a heuristic signal check. It does not prove intelligibility or replace listening. Report
measurements and the generated headphone-check timestamps; never claim the soundtrack sounds good.

## Know which output is finished

| File | Purpose |
|---|---|
| `renders/picture.mp4` | Intermediate renderer output before the pipeline's final soundtrack mix. It may already contain renderer-produced audio. |
| `renders/mix-premaster.wav`, `renders/mix.wav` | Intermediate soundtrack files. |
| Working directories and `video.tmp.mp4` | Temporary capture, encoding, or muxing output. |
| **`renders/video.mp4`** | **The render with the pipeline's final mixed soundtrack.** |

An old `video.mp4` may remain while a new render is running. Its existence alone is not proof that the current
attempt succeeded. After mixing, the render command also generates automatic sound records, encoded-picture
checks, and a source receipt. Allow it to finish and distinguish these stages from a new capture stall.

After the command exits successfully, confirm:

- The current `video.mp4` is nonempty and its duration, dimensions, frame rate, frame count, and audio streams
  match the intended job. Expected video frames are approximately duration × fps, rounded by the renderer.
- The compiled timeline includes every intended scene, with none missing.
- Current media and pixel checks pass, and `review/render-source.json` identifies the verified MP4 and sources.
- Remaining warnings and soundtrack limitations are recorded accurately.

Resume `next` for the normal independent review and delivery loop. A successful render or `draft-rendered` status
is not independent review approval. Only an explicit user request for a render-only handoff changes that scope;
do not carry a previous job's review waiver into other work. For normal completion, wait for `STATE: done` and
report `review/delivery.json`, soundtrack measurements, and the five headphone checks. After thumbnail selection,
upload the qualified MP4 to YouTube as unlisted and include its link; see [YouTube upload setup](youtube-upload.md).
